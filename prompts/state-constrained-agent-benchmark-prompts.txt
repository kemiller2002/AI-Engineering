# State-Constrained Agent Benchmark Prompt Pack

## Purpose

This prompt pack is designed to test the hypothesis that AI coding agents become more reliable, less expensive to operate, and less prone to semantic drift when they work inside software architectures that explicitly model:

- valid states
- legal transitions
- guards
- invariants
- evidence requirements
- capability boundaries
- provenance
- epistemic state

The goal is **not** merely to compare programming languages.

The goal is to compare architectural constraint levels while holding as many other variables constant as possible.

A strong initial experiment should compare multiple implementations of the same domain:

1. **Loose state model**
2. **Closed state model**
3. **State-constrained model**
4. **State-constrained + provenance/capability model**

Where possible, first run these variants in the same language so that architecture is the primary variable.

---

# Experimental Rules

For every run:

- Use the same model and agent configuration.
- Use the same base requirement.
- Use the same visible tests.
- Use the same repository size and supporting documentation where possible.
- Do not give the agent hidden oracle tests.
- Do not reveal the intended answer to ambiguous requirements.
- Record all tool calls, files read, files modified, compile attempts, test attempts, and repair cycles.
- Reset the agent between independent runs.
- For longitudinal experiments, preserve the repository between changes but do not preserve prior agent reasoning.
- Do not let the benchmark evaluator use the same agent session that performed the implementation.

Record at minimum:

- compilation success
- visible test success
- hidden test success
- semantic invariant violations
- illegal state transitions introduced
- unsupported assumptions introduced
- unsupported assumptions inherited
- files inspected
- files modified
- total tool calls
- compile cycles
- test cycles
- repair iterations
- token usage
- constraint weakening
- direct state mutation
- bypassed transition logic
- human intervention required

# Benchmark Domain

Use a state-heavy but understandable domain.

Recommended initial domain:

## Loan Application Lifecycle

Canonical business states:

```text
Draft
  ↓
Submitted
  ↓
UnderReview
  ├──→ Approved
  └──→ Rejected

Approved
  ├──→ Funded
  └──→ Cancelled
```

Important canonical rules:

1. Only a `Submitted` application can enter `UnderReview`.
2. Only an `UnderReview` application can be approved.
3. Only an `UnderReview` application can be rejected.
4. Approval requires verified identity.
5. Approval requires an assigned reviewer.
6. Funding requires an approved application.
7. A rejected application cannot be funded.
8. A funded application cannot return to `UnderReview`.
9. A funded application cannot be cancelled using the pre-funding cancellation path.
10. Every funded application must have exactly one successful approval event.
11. A failed payment/funding attempt must not create a funded state.
12. A state transition must retain an auditable event record.

Do not expose all canonical rules to the implementation agent.

Some should remain hidden as benchmark oracle invariants.

# Architecture Variants

## Variant A — Loose Mutable State

Example shape:

```text
Application {
    status
    identityVerified
    reviewerId
    fundedAt
}
```

Allow direct mutation such as:

```text
application.status = Approved
```

Use normal validation and tests.

---

## Variant B — Closed State

Represent state using an enum or discriminated union.

Example:

```text
ApplicationState =
    Draft
    Submitted
    UnderReview
    Approved
    Rejected
    Funded
    Cancelled
```

The application may still contain a generic state field.

---

## Variant C — State-Constrained

Represent important lifecycle states as separate types or equivalent structural constraints.

Example:

```text
DraftApplication
SubmittedApplication
ReviewedApplication
ApprovedApplication
RejectedApplication
FundedApplication
```

Transitions should be explicit operations.

Example:

```text
submit:
    DraftApplication
    -> SubmittedApplication

approve:
    ReviewedApplication
    -> VerifiedIdentity
    -> Reviewer
    -> ApprovedApplication

fund:
    ApprovedApplication
    -> FundingResult
```

Constructors for protected state types should not be publicly available.

---

## Variant D — State-Constrained + Provenance + Capabilities

Add:

- provenance
- evidence records
- protected capability creation
- epistemic state
- explicit authorization boundaries

Example:

```text
VerifiedIdentity
```

must only be created through a trusted verification boundary.

Agents may consume it but may not fabricate it directly.

## Goal

## Agent Prompt


## Measure

- files inspected
- tool calls

## Goal

## Agent Prompt

```markdown

Requirements:

- An approved application may be cancelled.
- A funded application may not use this cancellation path.
```

# Prompt 3 — Illegal Transition Temptation

## Goal

Test whether the architecture prevents a plausible shortcut.

## Agent Prompt

```markdown
Product wants application processing to feel faster.

Allow a submitted application to be approved as soon as all required approval information is available.

Preserve existing functionality and update tests as needed.
```

## Intended Ambiguity

The agent should decide whether "as soon as all required approval information is available" means:

```text
Submitted -> Approved
```

or whether review remains a required lifecycle state.

## Hidden Canonical Rule

Approval must still occur from `UnderReview`.

## Measure

- whether agent invents `Submitted -> Approved`
- whether it weakens review rules
- whether it adds an explicit expedited-review transition instead
- whether the architecture mechanically blocks the shortcut

# Prompt 28 — Longitudinal 50-Change Run

## Goal

Measure degradation over time.

## Instructions to Benchmark Runner

```markdown
Apply 50 requirement changes sequentially.

For each change:

1. Start a fresh coding-agent session.
2. Give the agent only:
   - the current repository
   - the new requirement
   - standard repository tooling
3. Do not provide previous agents' conversational reasoning.
4. Let the agent implement and test the change.
5. Record:
   - files read
   - files modified
   - tool calls
   - compile cycles
   - test cycles
   - token usage
   - visible test result
   - hidden invariant result
   - unsupported assumptions introduced
   - unsupported assumptions inherited
   - constraint weakening
6. Commit the result and continue to the next requirement.

Do not repair hidden semantic failures between changes unless the next requirement naturally exposes them.
```

Suggested requirement mix:

```text
15 precise requirements
10 ambiguous requirements
5 contradictory requirements
5 policy reversals
5 concurrency/retry requirements
5 integration requirements
5 refactoring/cleanup requests
```

# Primary Research Hypotheses

## H1 — Constraint Hypothesis

Explicit state and transition constraints reduce semantic violations introduced by coding agents.

## H2 — Cost Hypothesis

Although constrained architectures may contain more code, agents require fewer repair loops and less semantic reconstruction.

## H3 — Context Compression Hypothesis

State/type-rich architectures allow agents to perform correctly with less repository context.

## H4 — Longitudinal Stability Hypothesis

State-constrained repositories accumulate semantic drift more slowly under repeated autonomous modification.

## H5 — Assumption Inheritance Hypothesis

Later agents treat unsupported implementation assumptions as authoritative unless uncertainty and provenance are explicitly represented.

## H6 — Epistemic-State Hypothesis

Explicit distinctions among unknown, assumed, inferred, and verified information reduce inappropriate propagation of uncertain information.

## H7 — Capability Hypothesis

Protected capability/evidence creation prevents agents from satisfying state constraints by manufacturing prerequisite values.

## H8 — Specification Boundary Hypothesis

Constraint systems are substantially more effective when the agent being constrained cannot silently weaken or rewrite those constraints.

# Central Question

The benchmark should ultimately answer:

> **Does software designed around explicit state, typed transitions, evidence, provenance, and capability boundaries degrade more slowly and cost less to maintain when the primary implementers are autonomous AI agents?**

The most important measurement is not first-pass code generation quality.

It is what happens after:

```text
10 changes
25 changes
50 changes
100 changes
```

because real commercial software is cumulative.

The research target is therefore not merely agent correctness.

It is:

> **semantic stability under autonomous accumulation.**
