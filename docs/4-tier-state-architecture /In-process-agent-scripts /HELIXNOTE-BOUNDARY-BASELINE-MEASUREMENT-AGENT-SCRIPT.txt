# HelixNote Boundary-Cost Baseline and Measurement Mission

## Mission

Establish a reproducible **pre-optimization baseline** for the current HelixNote Four-Tier / State Programming implementation.

Do **not** redesign or materially refactor the application during this mission.

The purpose of this work is to measure the current architecture before boundary-consolidation experiments begin, preserve the exact repository state being measured, and create the instrumentation and reporting structure needed to compare future implementations objectively.

At the end of this mission:

1. the current branch and commit must be recorded;
2. the current commit must be tagged with a meaningful immutable Git tag;
3. the Four-Tier semantic architecture must remain unchanged;
4. the current boundary surface must be mapped;
5. baseline metrics must be recorded;
6. known architectural gaps must be documented;
7. all measurement scripts must be committed where appropriate;
8. the final report must clearly distinguish measured facts from inference.

---

# Research Question

We already have evidence that the Four-Tier architecture reduces reasoning effort inside the semantic core.

The unresolved question is:

> Does the reduction in semantic reasoning and defect propagation outweigh the cost of maintaining explicit boundaries?

This mission establishes the baseline needed to answer that experimentally.

Do not try to prove that State Programming is better.

Measure the current system.

---

# Core Hypothesis Being Tested Later

The current working hypothesis is:

> Explicit semantic boundaries reduce inference inside the protected system but may increase integration surface area. The architecture succeeds only if the reduction in semantic reasoning and defect propagation outweighs the cost of maintaining those boundaries.

This mission does not test the hypothesis directly.

It establishes the **before state**.

---

# Critical Constraint

## Do not optimize before measuring.

Do not:

- consolidate DTOs;
- introduce shared contracts;
- generate clients;
- introduce JSON Schema unless already present;
- introduce OpenAPI generation;
- change serializers globally;
- restructure tiers;
- eliminate mappings;
- change route architecture;
- change the WASM/browser kernel architecture;
- add a framework;
- introduce a custom State Programming DSL;
- move semantic types across boundaries.

Measurement tooling and documentation may be added.

Fix a defect only if it prevents accurate measurement. If that happens, stop and document the blocker before making the smallest possible correction.

# Phase 4 — Measure Boundary Surface Area

Create baseline counts.

At minimum measure:

## Structural counts

- number of semantic-to-host crossings;
- number of host-to-semantic crossings;
- number of API request DTOs;
- number of API response DTOs;
- number of WASM/browser message shapes;
- number of persistence record shapes;
- number of mapping functions;
- number of route declarations;
- number of client-side route representations;
- number of server-side route representations;
- number of independent representations of the same route;
- number of serializers/parsers involved;
- number of manually maintained boundary contracts.

## Semantic weakening counts

Count places where a constrained representation becomes weaker, including:

- DU → string;
- enum/closed case → string;
- value object → primitive;
- typed operation → generic method/body representation;
- semantic field → `(kind:string, field:string)`;
- typed identifier → unvalidated string;
- semantic state → generic JSON object;
- option/union → incidental serializer representation.

Do not assume every weakening is wrong.

Record it.

## Duplication counts

Identify semantic facts represented independently in more than one place.

Examples:

- routes;
- field names;
- entity-kind names;
- correction fields;
- operation names;
- discriminator strings;
- effect names;
- DTO shapes.

For each duplicated fact record:

```text
number of copies
locations
authority if one exists
agreement mechanism
```

## Exhaustiveness / wildcard counts

Count boundary-relevant matches containing:

- `_ ->`;
- default branches;
- catch-all field handling;
- generic fallback cases.

Record whether each wildcard is semantically justified.

Do not automatically classify all wildcard matches as defects.

## F# wire-risk counts

Audit boundary-facing DTOs for:

- `option`;
- raw discriminated unions;
- FSharpList;
- tuples;
- union cases;
- semantic-core types;
- framework-specific wrappers;
- nested combinations of these.

Produce counts by category.

This measurement is especially important because future work may attempt to mechanically prevent unsafe wire DTOs.

# Phase 5 — Measure Boundary Maintenance Cost Proxies

Create baseline metrics that future experiments can compare against.

## 1. Boundary Surface Area — BSA

Do not pretend there is already a scientifically validated formula.

Record the underlying counts first.

Optionally calculate an experimental composite:

```text
BSA =
    crossings
  + manual mappings
  + duplicated contract facts
  + independent wire representations
```

If using a composite score, label it explicitly as an **experimental metric**, not an established standard.

The raw values matter more than the combined number.

## 2. Boundary Change Amplification — BCA

For historical changes where Git history permits reliable reconstruction, estimate:

```text
BCA =
boundary files changed
per semantic decision
```

Do not invent semantic-decision counts.

If historical reconstruction would require guessing, defer this metric until controlled mutation experiments.

## 3. Decision Locality

Where are domain decisions currently located?

Count files containing:

- genuine semantic decisions;
- boundary decisions;
- mechanical propagation;
- presentation-only logic.

Create an initial classification where reliable.

## 4. Search-Space Reduction

Measure how much of the repository can be excluded when investigating particular classes of boundary issues.

Record:

- total relevant source files;
- semantic-core source files;
- API/host/boundary source files;
- percentage or count of repository excluded by architectural rules.

Do not interpret this as token savings yet.

It is a search-space proxy.

## 5. Mechanical Enforcement Coverage

Record which concerns are protected by:

- compiler;
- warnings-as-errors;
- architecture script;
- route agreement check;
- contract test;
- unit test;
- integration test;
- runtime validation;
- manual convention only.

This should produce a matrix.

Example:

```text
Concern                         Enforcement
-------------------------------------------------------
Semantic dependency leak        architecture script
Missing DU case                 FS0025 / compiler
GET with body                   closed HttpEffect type
Route mismatch                  route agreement script
Unsafe option wire DTO          convention only
Unknown external JSON           runtime parser
```

This is one of the most important baseline artifacts.

# Phase 9 — Establish Change Classification

For all future HelixNote experiment work, use these four categories:

## Semantic Change

Changes:

- legal meaning;
- legal states;
- transitions;
- invariants;
- capability;
- evidence;
- obligation;
- uncertainty semantics;
- effect semantics.

## Boundary Change

Changes:

- representation;
- serialization;
- routes;
- host contract;
- persistence shape;
- external protocol.

## Mechanical Propagation

No new semantic or boundary decision.

Change is compiler-, schema-, generation-, or contract-directed.

## Presentation Change

Display/UI only, unless presentation itself carries domain meaning.

Include these classifications in the baseline metrics format so future work can count them consistently.

# Interpretation Guardrails

Do not conclude:

> Four-Tier is more productive.

Do not conclude:

> Four-Tier creates too many boundaries.

Do not conclude:

> Boundary duplication proves the tiers should collapse.

Do not conclude:

> A green semantic core proves the system is correct.

This mission establishes the evidence needed to test those questions later.

The current evidence only supports a narrower observation:

> HelixNote's Four-Tier architecture has made semantic modification and semantic isolation mechanically safer, while the cost and defect behavior of its explicit boundary surface remain an open research question.

Measure that surface before changing it.
